# 백엔드 요청 — Docker 운영 구성 정리 · 모니터링 이전 · 헬스 체크

- 보낸 곳: deskless (2026-11-23)
- 받는 곳: [deskless-backend](https://github.com/HaSungJe/deskless-backend)
- 기준 커밋: `d71623e` — 지우는 파일의 원본은 이 커밋에 남는다(deskless 가 여기서 옮겨 간다)
- 공개 API · 사용자 동작 변화: 없음 → 프론트 수정 요청 문서(`.beaver/output/frontend/changes/`) 대상 아님

## 왜

deskless 저장소가 백엔드 · 프론트를 쿠버네티스(k3s · Helm)로 엮는다. **"어떻게 띄우는가"**(인스턴스 수 · 로드밸런서 · 네트워크 · 인프라 · 지표 수집 · 대시보드)는 deskless 가 맡고, 백엔드는 **"무엇을 띄우는가"**(앱 코드 + `Dockerfile`)만 갖는다.

지금 백엔드는 Docker compose 를 전제로 인스턴스 수(`*_REPLICAS`) · nginx 로드밸런서 · 공용 네트워크 · 인프라 묶음 · Prometheus 수집 대상(프론트 `web` 포함)까지 직접 갖고 있어 배포 구성과 앱이 섞여 있다.

### 정해진 것 (사용자 결정 2026-11-23)

- **compose 는 전부 지운다** — 백엔드에는 `Dockerfile` · `.dockerignore` 만 남긴다. 개발할 때 쓰는 인프라(PostgreSQL · RabbitMQ · Redis)도 deskless 클러스터에서 띄운다.
- **운영 중인 서버가 없다** — deskless 차트를 기다리지 않고 바로 정리한다.
- **앱 지표 코드(`libs/monitoring`)는 백엔드에 남는다** — `/metrics` 를 내는 쪽은 앱이다. 모으고 보는 쪽(Prometheus · Grafana · 수집기 · 기록 규칙 · 대시보드 JSON)만 deskless 로 간다.
- **헬스 체크** — 지표 전용 포트에 `/health/live` · `/health/ready`, 준비 판단은 앱 상태만(아래 2절).
- "로드밸런싱 전제"(인스턴스 로컬 상태 금지 · sticky 불필요 · crontab 은 `JobLockService`) 원칙은 쿠버네티스에서도 그대로라 남긴다 — 바뀌는 것은 그 숫자와 장치를 어디서 정하느냐뿐이다.

## 2. 더하는 것 — 헬스 체크 (쿠버네티스 프로브)

### 계약

| 경로 (지표 전용 포트) | 200 | 503 |
|---|---|---|
| `GET /health/live` | 프로세스가 응답하면 항상 | — |
| `GET /health/ready` | 부팅 완료 + (HTTP 앱은) 본 포트가 요청을 받는 중 + 종료 시작 전 | 부팅 중 · 종료 중 |

- 상태 코드가 계약이다 — 본문은 프로브가 보지 않는다(짧게 `{"status":"ok"}` · `{"status":"not_ready"}`).
- **DB · 브로커 · Redis 는 보지 않는다** — 지금 설계가 "없어도 부팅하고 그 요청만 503"(`libs/messaging/src/rabbitmq.connection.ts:28`)이라, 의존 서비스가 잠깐 끊길 때 모든 파드가 한꺼번에 준비 안 됨이 돼 조회 · 로그인까지 막히는 일을 피한다.
- 앱 4개 모두(gateway · user-service · admin-service · scheduler).

### 왜 지표 전용 포트인가 (본 포트가 아닌 이유)

- user-service · admin-service 본 포트는 모든 HTTP 요청에 내부 토큰을 요구한다(`apps/user-service/src/user-service.module.ts:50` · `apps/admin-service/src/admin-service.module.ts:50`) — 프로브는 비밀값 헤더를 싣기 어렵다.
- gateway 본 포트는 모든 요청을 API 로그 DB 에 적재한다(`apps/gateway/src/gateway.module.ts:72`) — 프로브(파드마다 수 초 간격)가 `t_api_log` 를 채운다.
- 지표 서버는 Nest 컨트롤러가 아닌 별도 `node:http` 서버라(`libs/monitoring/src/metrics.server.ts:32`) 가드 · 미들웨어 · HTTP 지표에 섞이지 않고, scheduler 도 이 포트 하나는 이미 연다.

### 구현 메모 (근거)

- `MetricsServer` 의 라우팅(`metrics.server.ts:33` — 지금은 `/metrics` 외 404)에 두 경로를 더하고, 경로 상수는 `METRICS_PATH` 옆(`monitoring.constants.ts:5`)에 둔다.
- **본 포트 listen 확인이 필요하다** — HTTP 앱은 `app.listen()` 이 초기화(onApplicationBootstrap — 지표 서버가 이때 열린다)를 먼저 하고 그 뒤에 본 포트를 연다(`apps/gateway/src/main.ts:37`). 그래서 "지표 서버가 열림 = 준비됨" 이 아니다 — HTTP 앱(`MonitoringOptions.http === true`)은 `HttpAdapterHost.listening` 을 본다(Nest 12.1 — listen 뒤 true `node_modules/@nestjs/core/nest-application.js:316`, 본 포트를 닫을 때 false `:68`). scheduler(`http: false`, `createApplicationContext` — `apps/scheduler/src/main.ts:11`)는 부팅 완료면 준비됨.
- **종료** — `enableShutdownHooks` 로 종료 신호를 받으면 Nest 12.1 은 prepareClose → onModuleDestroy → beforeApplicationShutdown → 본 포트 닫기(dispose) → onApplicationShutdown 순으로 부른다(`node_modules/@nestjs/core/nest-application-context.js:158-162`). 준비 상태는 앱 훅 중 가장 먼저(onModuleDestroy) 503 으로 바꾸고, live 는 지표 서버가 닫힐 때(onApplicationShutdown — `metrics.server.ts:50`)까지 200.
- 종료 전 대기(preStop sleep) · 종료 유예 시간은 deskless 차트가 맡는다 — 앱 코드에 지연을 넣지 않는다.
- 테스트: 라이브러리 · 인프라라 spec 을 두지 않는다(`docs/testing.md` · `docs/monitoring.md` 테스트 절). `npm run typecheck` · `npm run build` 로 확인하고, 실제 응답은 사용자가 앱을 띄워 확인한다.

배포 · 실행 설명은 "deskless 저장소(쿠버네티스)" 한 줄 안내로 바꾸고, 앱 규칙은 남긴다.

| `AGENTS.md` | 구조 트리의 `docker/` · `scripts/`(docker-network 빠짐) 줄 · 주의사항 "서버 · 인프라 기동"(`npm run docker:*` 목록 → 클러스터 명령은 deskless 규칙) · "DB 마이그레이션 적용"(Docker migrate 컨테이너 → deskless 마이그레이션 Job) · Key Patterns "Docker 실행 — 묶음 8개" 문단(→ 이미지 규칙 `Dockerfile` · `APP` 인자 · Node 고정만 남기고 배포는 deskless) · "`.env` 하나가 곧 서버 설정"(compose 언급 → deskless) · 모니터링 절(Docker 9464 고정 · `compose.monitoring.yml` · 기록 규칙 · 대시보드 JSON → deskless, 지표 · 헬스 체크 전용 포트로) · 실시간 소켓 절(nginx `/ws/` → deskless Ingress) · 체크리스트 모니터링 항목 |

## 4. 그대로 두는 것

- `Dockerfile` · `.dockerignore` — deskless 가 `backend/` 를 빌드 컨텍스트로 `APP` 인자(gateway · user-service · admin-service · scheduler)로 이미지 4개를 만든다.
- 앱이 읽는 env 와 그 기본 동작: `GATEWAY_INSTANCE_ID`(비면 호스트명 = 파드 이름) · `TRUST_PROXY` · `*_METRICS_PORT` · `METRICS_HOST` · `FILE_STORAGE_DIR` · `*_SERVICE_HOST` · `*_SERVICE_PORT` · `USER_SERVICE_URL` · `ADMIN_SERVICE_URL`(deskless 가 Service 주소로 넣는다).
- `libs/monitoring` 의 지표 코드 · 지표 이름 · `service` 라벨.
- `scripts/check-broker-acl.mjs`(`npm run broker:check`) · `db-schema.mjs` · `sample-images.mjs`.
